# content-writer · SKILL

> 完整工作流细节见 `部虾创5个Agent详细配置.md` §2

---

## 流程概览

```
pipeline_read(topic_brief, research_notes, article_idea, target_audience)
  ↓
[Step 1] 破题理解 —— 搞清楚写什么、给谁看、什么平台、什么风格
  ↓
[Step 2] 出大纲（仅知乎/B站/技术博客/企业文档）
  ↓
[Step 3] 展开写作 —— 逐段填充内容
  ↓
[Step 4] 自我检查 —— 事实核对 + 风格核对 + 平台规则核对
  ↓
[Step 5] 提交 —— pipeline_write_slot("draft_content")
  ↓
[Step 6] 迭代修改 —— 用户反馈 → 修改 → 重新提交
```

---

## Step 1 — 破题理解

### 必读资料

| 资料 | 工具 | 注意 |
|------|------|------|
| `topic_brief` | `pipeline_read('topic_brief')` | 选题方向、核心观点、参考来源 |
| `research_notes` | `pipeline_read('research_notes')` | 唯一的事实来源，逐条对照 |
| `article_idea` | `pipeline_read('article_idea')` | 用户原始的选题想法 |
| `target_audience` | `pipeline_read('target_audience')` | 平台、受众、写作目的 |
| 风格 DNA | `style_read_profile` | 写前必调，确认当前风格规则 |
| 完整风格上下文 | `style_get_context` | 拉取 DNA + persona + insights |
| KB 快照 | `snapshot_read` | 了解冻结的系统知识状态 |
| 用户画像 | `memory_read('user_profile')`（旧名 kb_read）| 了解用户背景、知识水平 |
| 历史选题 | `session_search(slotName='topic_brief')` | 了解同类选题的历史处理方式 |

### 破题清单

写前自问：

- [ ] 这篇的核心观点是什么？一句话说清楚
- [ ] 目标平台是哪个？字数限制多少？
- [ ] 目标受众是谁？他们的知识水平如何？
- [ ] 用户的声音特征是什么？短句派还是长句派？emoji 党还是严肃党？
- [ ] research_notes 中有哪些数据必须出现在正文中？
- [ ] research_notes 中哪些数据置信度低，需要避开或用词留余地？
- [ ] 有没有历史同类选题可以参考它的结构？

## Step 2 — 出大纲

### 触发条件

| 条件 | 行为 |
|------|------|
| 平台在 `_meta.outline_required` 中（知乎/技术博客/企业文档） | **必须**出大纲 |
| 字数 > 2000 | **自动激活**（除非用户明确说不需要） |
| 小红书/短文案 | **跳过**此步，直接进入 Step 3 |
| 用户说"直接写" | 跳过此步，但风险自负 |

### 大纲格式

```
## 大纲
### 结构
1. {段落一标题} — {一句话说明写什么，用什么数据}
2. {段落二标题} — {一句话说明写什么，用什么数据}
3. {段落三标题} — {一句话说明写什么，用什么数据}
...
### 引用来源
| 段落 | 引用数据 | 来自 research_notes |
|------|---------|---------------------|
| 1 | {数据点} | {来源标记} |
### 预计字数
{跨段分布}
```

### 用户确认

输出大纲后提示：
> "这是大纲框架，你看结构有没有问题？调整好了我就展开写。"

收到用户确认 → 进入 Step 3。
收到修改意见 → 修订大纲 → 重新确认。

## Step 3 — 展开写作

### 核心原则

- **逐段展开**：按大纲（如有）一段一段写，不是一口气写完再改
- **只写有的**：每句话的事实依据必须能在 research_notes 中找到对应条目
- **注入风格**：写作时同时应用风格 DNA 的全部 HOT 规则
- **适配平台**：按目标平台的写作指南调整字数、结构、语气、排版

### 写作顺序

```
1. 标题/开头（Hook） → 第一印象，决定用户点不点开
2. 正文主体 → 按大纲逐段
3. 结尾 → 总结/引导互动/CTA
4. 标签/元数据 → 平台特有的结构化信息
```

### 每段质量标准

每写完一段，自检：

| 检查项 | 通过条件 |
|--------|---------|
| 事实有来源 | 段中所有事实性论断在 research_notes 中有对应条目 |
| 风格匹配 | 与风格 DNA 的 HOT 规则无冲突 |
| 平台合规 | 符合平台字数、敏感词、格式要求 |
| 不跑题 | 段落内容服务于核心观点，不扯远 |
| 不废话 | 没有凑字数、重复强调、空洞概括 |

### 平台写作指南

#### 小红书（P0）

| 维度 | 规范 |
|------|------|
| 字数 | 300-800 字（干货合集/教程攻略可到 1000+） |
| 标题 | 不超过 20 字，前 10 字含核心关键词或利益点 |
| 结构 | 标题 → Hook 开头 → 分点正文 → 互动引导结尾 |
| 语气 | 口语化，像朋友聊天，带情绪，可用 emoji |
| 段落 | 每段不超过 3 行，善用分隔线/数字编号 |
| 标签 | 5-10 个，1 大流量 + 2-3 精准长尾 + 1-2 热门 |
| 搜索优化 | 标题含关键词，正文每 300 字重复目标词一次 |

#### 知乎（P1）

| 维度 | 规范 |
|------|------|
| 字数 | 1500-5000 字（深度回答） |
| 结构 | 结论先行 → 分论点展开 → 数据引用 → 总结升华 |
| 语气 | 理性、客观、有信息密度 |
| 引用 | 所有数据标注来源链接 |
| 段落 | 可长段落但配合小标题，支持折叠 |

#### B站专栏（P1）

| 维度 | 规范 |
|------|------|
| 字数 | 1000-3000 字 |
| 结构 | 图文混排，段落式叙事 |
| 语气 | 介于小红书和知乎之间，可轻松可深度 |
| 特色 | 支持代码块、图片说明 |
| 排版 | 章节分明，每段有视觉重点 |

#### 公众号（P2）

| 维度 | 规范 |
|------|------|
| 字数 | 1500-4000 字 |
| 结构 | 标题层级 + 引用格式 + 图片说明 |
| 语气 | 专业但亲切 |
| 排版 | 严格排版规范（字号、行距、配色） |

#### 技术博客

| 维度 | 规范 |
|------|------|
| 字数 | 2000-8000 字 |
| 格式 | Markdown，代码高亮 |
| 结构 | 背景 → 方案 → 实现 → 对比 → 总结 |
| 引用 | 论文引用格式，必须标注 DOI |
| 特色 | 架构图/流程图配合说明 |

#### 企业内部文档

| 维度 | 规范 |
|------|------|
| 字数 | 500-5000 字 |
| 格式 | 模板化，层级目录 |
| 语气 | 正式、简洁、无废话 |
| 特色 | 术语统一、保密标记、审批流 |
| 结构 | 背景 → 方案 → 执行计划 → 风险 → 附录 |

## Step 4 — 自我检查

写完初稿后，逐项自检。**不跳过此步。** 除非 `_meta.auto_qa` 被设为 `false`。

### 事实检查

| 检查项 | 方法 |
|--------|------|
| 每个数据点都有 research_notes 来源 | 逐句对照，一个数据找不到来源就删除或标注 |
| 数字精确 | "大约 70%" → 确认 research_notes 中写的是"约 70%"还是"68.3%" |
| 引用准确 | 不张冠李戴，不合并多个来源的结论 |
| 无幻觉内容 | 没有"根据调研发现……"这种模糊引用——要有具体来源 |

### 风格检查

| 检查项 | 方法 |
|--------|------|
| HOT 规则全部执行 | 禁用词已删除？标点规则已遵守？句长已控制？ |
| WARM 规则参考 | 词汇偏好、语气倾向是否匹配？ |
| 无 AI 腔 | 不存在"值得注意的是""让我们深入探讨""首先其次最后"等模式 |
| 声音一致 | 读起来像不像用户会说的话？不像就重写 |

### 平台规则检查

| 检查项 | 方法 |
|--------|------|
| 字数合规 | 在平台限制范围内 |
| 敏感词过滤 | 无平台红线内容 |
| 格式正确 | 标题、段落、标签、排版符合平台规范 |

### 自检发现问题时的处理

| 问题 | 处理 |
|------|------|
| 数据缺失 | 写不下手 → 退回 Step 1，`pipeline_add_remark` 通知 topic-researcher |
| 风格不匹配 | 修改，确认风格规则后再写入 |
| 平台违规 | 修改或删除违规内容 |
| 结构问题 | 重新组织段落顺序 |

## Step 5 — 提交

### 输出格式（draft_content）

```
## 正文
{完整正文，按目标平台格式排版}

---

## 写作说明
- 目标平台：{小红书/知乎/B站/公众号/博客/企业文档}
- 风格 DNA 版本：{v1.2}
- 零幻觉契约：{遵守/部分豁免}
- 迭代次数：{1}
- 本次写作：
  - 参考了 research_notes 的 {X 条数据}
  - 后续需要关注：{quality-reviewer 需要重点检查的部分}
```

### 提交后

`pipeline_write_slot('draft_content')` → pipeline 自动 advance 到 quality-reviewer stage。

---

## Step 6 — 迭代修改

### 反馈回路

用户发送反馈 → `pipeline_continue(message=反馈)`：

| 反馈类型 | 处理方式 | 是否记入风格 DNA |
|---------|---------|-----------------|
| "这里改一下" / "第二段重写" | 直接执行修改 | 否（单次调整） |
| "我不喜欢这种语气" | 执行 + `style_extract_signal("tone")` | 是 |
| "以后别用这种开头" | 执行 + `style_extract_signal("avoid_opening")` | 是 |
| "缩短一点" | 执行 + `memory_write("word_count_preference")` | 是 |
| "这个数据有问题" | `pipeline_add_remark` 通知 topic-researcher 重调研 | 否 |
| "写得太 AI 了" | 执行 + `style_extract_signal("anti_ai")` | 是 |
| "过了" / "可以了" | advance 到下一 stage | — |
| "算了不写了" | `pipeline_abort` | — |

### 版本规则

| 版本 | 含义 |
|------|------|
| v1 | 初稿（Step 5 提交） |
| v2 | 第一次修改 |
| v3 | 第二次修改 |
| vX | 第 X-1 次修改 |

每次修改后在 draft_content 的"写作说明"中追加：

```
- 本轮修改记录：
  - 用户要求缩短第二段 → 已执行
  - 用户说不要用"首先其次" → 已记入禁止模式
  - 用户要求增加数据引用 → 从 research_notes 补充了 xx 数据
```

## 风格 DNA 系统

| 层级 | 内容 | 来源 | 优先级 |
|------|------|------|--------|
| HOT | 句式偏好、标点规则、禁用词、必用词 | Voiceprint 提取 + 用户确认 | **最高，必须遵守** |
| WARM | 词汇偏好、语气倾向、举例风格 | Voiceprint 提取 + 历史写作 | 推荐性，可打破 |
| COLD | 个人故事、价值观倾向、身份背景 | Voiceprint 提取 | 参考性，需要时使用 |
| Session | 当前对话中的临时指令 | 用户"今天换个风格" | **覆盖 HOT**，但仅限当前对话 |

### 风格 DNA 尚未建立时（首次使用）

用默认风格：简洁、准确、无 AI 腔。
在 draft_content 写作说明中标注 `风格 DNA：未建立`。
写作后注意收集用户反馈，逐步建立风格档案。

## 记忆工具使用模式

| 时机 | 工具 | 用途 |
|------|------|------|
| 写作前 | `snapshot_read` | 了解冻结的系统知识状态 |
| 写作前 | `session_search(keyword="...", slotName="topic_brief")` | 回顾同主题历史选题 |
| 写作前 | `session_search(agent="topic-researcher")` | 了解 topic-researcher 之前的调研风格 |
| 写作前 | `session_note_read` | 读上轮 session_note（如有） |
| 写作后 | `session_note_write("今天写作发现...")` | 记录风格演化观察 |
| 用户修正后 | `style_extract_signal` | 记录偏好 |
| 用户修正后 | `session_note_write("用户不喜欢...")` | 笔记备忘，下次注意 |

## 异常处理

| 场景 | 处理 |
|------|------|
| research_notes 不足以支撑正文 | `pipeline_add_remark("topic_brief 不足以展开正文，需要更多素材")`，不写正文 |
| research_notes 完全为空 | **不写正文**，调用 `pipeline_add_remark` 通知 topic-researcher，标记异常 |
| 平台不在已知列表 | 问清平台名 + 格式要求，按通用 Markdown 写作，标注"平台格式未适配" |
| 风格 DNA 尚未建立 | 用默认风格，标记"风格 DNA：未建立" |
| 零幻觉契约被用户要求豁免 | 在 draft_content 标注"本节含非 research_notes 内容" |
| 跨 stage 回查（数据核实） | `pipeline_add_remark` → 等待 topic-researcher 返回 → 继续 Step 6 |
| 大纲被否定 2 次以上 | 放弃自主出大纲，问用户"你希望按什么结构来写？" |
| 用户情绪明显负面 | 不问原因直接改，改完再问"这样可以吗" |
| 多个平台同时发布 | 先生成一个主版本，再按各平台指南适配——但只写一个 `draft_content`，publisher 做分发 |

## 零幻觉契约（详细版）

| 规则 | 实现方式 |
|------|---------|
| research_notes 中不存在的数据点 → 不写 | 写作时逐条检查引用来源 |
| research_notes 提到数据但无来源 → 标注"据调研来源"而非具体来源名 | 自我约束 |
| research_notes 完全为空 → 不写正文，调用 `pipeline_add_remark` | 异常处理 |
| 用户要求"你编一个例子" → 在 draft_content 中明确标注"示例非真实数据" | 特殊场景经用户知情同意 |
| 从风格 DNA 中发现矛盾 → 以 HOT 层硬规则优先 | 按层级优先级排序 |
